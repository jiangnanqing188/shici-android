# 应用内更新检查与安装（测试版渠道）

本文件只说明**应用内更新模块**的行为、发布约定与已知边界。它不改变版本号、不发包、不替代人工发布，也不承诺真实设备验收。

## 1. 一句话

应用启动或回到前台后，**限频**读取一次 GitHub 的公开发布列表；如果本渠道存在版本号更高、且校验信息完整的测试包，就在页面顶部用一条**非阻塞**提示条告知，并在「设置 → 关于」提供手动检查、下载、校验与安装入口。下载与安装都只由用户点击触发，安装由系统安装器确认，应用从不静默安装。

## 2. 渠道（tablet / phone）

- 渠道由**构建源码里的非本地化字符串资源**决定：`app/src/main/res/values/update_channel.xml` 的 `update_channel`，平板为 `tablet`，手机为 `phone`。同一资源也成为 APK 清单里的渠道标记。
- 不使用设备形态、屏幕宽度、语言或地区推断渠道；该资源不做翻译（`translatable="false"`）。
- 值不是 `tablet`/`phone` 时，更新检查直接停用（设置页显示"本构建未配置更新渠道"），不会猜测、也不会退化成"已是最新"。

## 3. 认可的发布

仓库固定为 `jiangnanqing188/shici-android`，接口固定为：

```
GET https://api.github.com/repos/jiangnanqing188/shici-android/releases?per_page=100
```

（用列表接口而不是 `/latest`，因为测试版是 prerelease；响应体硬上限 2 MiB。）

一条发布只有在**全部**满足下面条件时才算候选：

| 条件 | 要求 |
|---|---|
| Tag | `v<major.minor.patch>-<channel>-test`，如 `v2.9.0-tablet-test` |
| 状态 | `draft=false` 且有有效的 `published_at`；`prerelease` 允许（测试版就是 prerelease） |
| 附件名 | `shici-<channel>-<versionName>-<versionCode>.apk`，与 tag 中的版本名、附件中的版本号完全一致 |
| 附件状态 | `state=uploaded` |
| 校验值 | `digest` 为 `sha256:<64 位小写十六进制>` |
| 大小 | 1 字节 ~ 300 MiB（当前包约 158 MB） |
| 下载地址 | 必须**精确等于** `https://github.com/jiangnanqing188/shici-android/releases/download/<tag>/<附件名>` |

选择规则：取本渠道的**数值最大 versionCode**，而非按版本名或发布时间排序。只提供严格高于已装版本的唯一新版。若本渠道存在名称不规范、缺失或重复的 APK，无法确定版本号时停止；最高候选的大小、状态、校验值或地址有误也不退选。

## 4. 下载

- 只访问固定 HTTPS 主机：`api.github.com`（列表）、`github.com` + `release-assets.githubusercontent.com` + `objects.githubusercontent.com`（资产）。跳转只可到两个资产域，必须 HTTPS、标准端口、无 userinfo 或 fragment；最多 5 跳；列表接口出现重定向直接失败。
- 不发送任何凭据、Cookie、设备 ID、账号或使用数据；应用不提交账号或学习内容。
- 下载按发布声明的字节数**边下边写**到应用私有缓存 `cache/updates/staging/`，最多写入声明大小；服务器声明大小与发布信息不一致、实际长度不符、SHA-256 不符都会丢弃文件。
- 传输超时：连接 10 秒、单次读取 20 秒；检查 45 秒、下载 15 分钟的期限在线程收发边界核对。

## 5. 校验与安装链

只有以下全部通过，文件才会被移动到 `cache/updates/verified/` 并交给安装器：

1. 长度 = 发布声明大小；SHA-256 = 发布声明的 `digest`；
2. `PackageManager.getPackageArchiveInfo` 读到包名 `com.shici.app`；
3. 版本号精确相等且比已安装版高（API 28+ 用 `longVersionCode`）、版本名和 APK 内渠道标记精确相等；
4. 签名证书集合与**已安装应用当前证书集合**完全一致（API 26/27 `GET_SIGNATURES`；28+ `SigningInfo.apkContentsSigners`，非空）。不同签名、转签拒绝，不支持降级安装。现有测试包的签名不是正式发行签名。

通过后用 `androidx.core` 的 `FileProvider` 生成只读 content URI（只授权 `cache/updates/verified/` 一个子目录，不暴露其它缓存），带一次性读权限交给系统安装器。`CanRequestPackageInstalls` 未允许时：解释原因，并只在用户点击时打开**本应用自己的**"安装未知应用"设置页；返回后需再点一次安装。启动安装器只代表"已打开系统安装器"，**不代表已安装**。

## 6. 时机、限频与生命周期

- 检查在 `onStart` 之后进行，跑在更新模块自己的单线程上（不占主线程、不占既有业务 worker），间隔 **24 小时**；失败按 15 分钟起、指数退避、上限 6 小时重试。手动检查绕过间隔，但不会与进行中的检查/下载重复请求。
- 上一次结论（已是最新 / 尚无发布 / 可下载的版本）持久化在 `update_prefs`，旋转或重建后直接显示，不必再发请求。
- 一条非阻塞提示条放在页面 body 之上的独立 wrapper 中，随布局占位，不覆盖导航、滚动、insets、新手引导、编辑器或系统权限窗口；「稍后」只对当前界面实例里的该版本隐藏提示条，设置入口始终保留。
- 离开前台（`onStop`）会让本次检查结果作废并**中止下载**，未完成的临时文件被删除；提示为"离开应用会中止本次下载"。旋转视同离开：下载需要重来，已保存的检查结论仍在。
- 不申请通知权限、不做推送、不启动常驻服务、不自动重试下载。旧缓存：只清理两个更新缓存目录内超过 7 天的文件；每次下载使用独立文件，不会覆盖或立即删除安装器可能还在读取的文件。

## 7. 发布方约定

- 手机与平板**各自维护单渠道递增的版本号**；同一渠道内不得回退 `versionCode`。
- 发布 APK 必须与已有安装包**同签名**（否则应用会拒绝；请勿以卸载绕过签名不一致）。
- 用对应渠道源码构建，验证 APK 内渠道标记、最终 APK 的证书与版本号，再按上表发布附件。内置更新只可安装带渠道标记的新包。

## 8. 当前边界

- **2.8.0 / versionCode 55 及更早的安装包没有本模块**，需要用户手动升级一次才会带上更新检查。
- 更新只认 GitHub Releases；不发包、不改版本号、不上传 APK 到任何第三方。
- 未做真实设备验收：网络中断/限流/超大的真实响应、系统安装器各厂商行为、未知来源设置的返回路径、真实下载耗时与耗电都需实机确认。
- 不做增量更新、断点续传、后台下载或静默安装；下载失败只能重新点击。
